01
DI & Servicios

¿Qué es DI?

La idea

  • Patrón de diseño: los objetos no crean sus dependencias
  • Las reciben de afuera — alguien más decide cómo construirlas
  • Resuelve el acoplamiento fuerte y abre la puerta a testing real
  • Angular trae su propio sistema: el Injector

¿Qué trae a la mesa?

Desacoplamiento

El componente no sabe cómo se construye el servicio

Testabilidad

Reemplazar dependencias por mocks en tests

Singletons

Una sola instancia compartida automáticamente

01
DI & Servicios

SIN DI vs CON DI

❌ Sin DI — acoplado

class BookList { private service = new BookService(); // crea su propia dependencia }
  • Difícil de mockear en tests
  • Cada componente crea su propia instancia
  • No se puede sustituir la implementación

✅ Con DI — desacoplado

class BookList { private service = inject(BookService); // la recibe del Injector }
  • Angular decide qué instancia entregar
  • Misma instancia compartida (singleton)
  • En tests: providers override por mocks
01
DI & Servicios

La función inject() (v14+)

Forma preferida en Angular moderno — funciona en cualquier contexto de inyección.

import { inject } from '@angular/core'; export class BookListComponent { // En la inicialización del campo — más limpio que el constructor private bookService = inject(BookService); // optional: true → null si no está registrado private logger = inject(LoggerService, { optional: true }); // InjectionToken — no necesita @Inject() private appConfig = inject(APP_CONFIG); } // Funciona fuera de clases también (guards, interceptores): export const authGuard: CanActivateFn = () => { const router = inject(Router); ... };
01
DI & Servicios

inject() vs constructor injection

Constructor (sigue válido)

constructor( private bookService: BookService, @Optional() private logger: LoggerService | null, @Inject(APP_CONFIG) private cfg: AppConfig, ) {}

Con inject() — más limpio

private bookService = inject(BookService); private logger = inject(LoggerService, { optional: true }); private cfg = inject(APP_CONFIG);

Sin decoradores extras: inject() reemplaza @Optional() y @Inject() con su segundo argumento.

01
DI & Servicios

@Injectable & el patrón Singleton

Declarar el servicio

// services/book.service.ts @Injectable({ providedIn: 'root' }) export class BookService { readonly createdAt = new Date(); private books: Book[] = []; getBooks() { return this.books; } addBook(b: Book) { this.books.push(b); } }

providedIn: 'root'

  • Singleton global — UNA sola instancia en toda la app
  • Tree-shakeable — Angular lo elimina si no se usa
  • No hace falta registrarlo en providers

Demo singleton: inyectá el mismo servicio en dos componentes y comparalos por createdAt — es la misma instancia.

providedIn: 'module' está deprecado desde Angular 15.

02
Providers

Dónde vive el servicio — 4 escenarios

Click en cada caja para ver el diagrama en grande

1. providedIn: 'root' — instancia global

Una sola instancia compartida por toda la app. Cualquier componente que la pida recibe la misma.

2. providers en A — solo A y sus hijos

La instancia nace al crearse A y muere con A. B y B1 no la ven — si la piden, error o lookup hacia el root.

3. Global + override en subtree

A redeclara la clase en sus providers: el subtree de A obtiene S' (nueva). Fuera del subtree, sigue resolviendo al S global.

4. Subtrees hermanos — dos instancias

Cada hermana declara su propio provider: dos instancias completamente distintas, una por subtree. No comparten estado.

Regla mental: el Injector busca el provider más cercano subiendo el árbol — la instancia vive mientras viva el componente que la declaró.

02
Providers

Declarar providers en un componente

El array providers en @Component materializa los escenarios 2-4: scope acotado al subtree.

A nivel de componente

@Component({ selector: 'app-feature', standalone: true, imports: [...], providers: [ // instancia nueva, solo para este componente // y sus descendientes LoggerService, // config local a este subtree { provide: APP_CONFIG, useValue: { theme: 'dark' } }, // override de un servicio global { provide: ApiService, useClass: MockApiService }, ], template: `...` }) export class FeatureComponent { // recibe la instancia "local" private log = inject(LoggerService); }

vs. providers globales

// app.config.ts — global, una sola // instancia para toda la app export const appConfig: ApplicationConfig = { providers: [ provideRouter(routes), { provide: LoggerService, useClass: ConsoleLogger }, ], };

¿Cuándo usar uno u otro?

  • Global — servicios compartidos (HTTP, auth, store)
  • Componente — estado local, mocks en tests, configuración por feature
  • Componente — necesitás una instancia nueva por componente (ej: una grilla con su propio paginador)

Regla: los providers de un componente ganan sobre los del root para ese subtree. Es exactamente el escenario 3 del diagrama anterior — override scoped.

02
Providers

Las 4 formas de proveer

provider cuándo usarlo
useClassSustituir una clase por otra (mock en tests, variante prod/dev)
useValueProveer un valor constante (config, flags)
useFactoryConstruir con lógica — decidir la implementación en runtime
useExistingAlias — redirigir a otro token ya registrado
// app.config.ts providers: [ { provide: LoggerService, useClass: SilentLoggerService }, { provide: APP_CONFIG, useValue: { maxBooks: 100, currency: 'ARS' } }, { provide: LoggerService, useFactory: () => environment.production ? new SilentLoggerService() : new VerboseLoggerService() }, { provide: OldLogger, useExisting: LoggerService }, ]
02
Providers

InjectionToken — inyectar lo que no es clase

¿Por qué?

  • No podés usar una interface como token — desaparece al transpilar a JS
  • Para strings, objetos de configuración, flags
  • Type-safe gracias al generic <T>

Definir y usar

// tokens/app-config.token.ts export const APP_CONFIG = new InjectionToken<AppConfig>('APP_CONFIG'); // providers { provide: APP_CONFIG, useValue: { appName: 'BookStore' } } // en el componente private cfg = inject(APP_CONFIG);

03
Observables

Observable & Observer Pattern

El concepto

  • Observable: secuencia de valores que llegan en el tiempo
  • Observer: el que reacciona a esos valores
  • Lazy: no emite nada hasta que alguien hace subscribe
  • Útil para HTTP, eventos del DOM, WebSockets, intervalos

Crear y consumir

import { Observable, of } from 'rxjs'; // desde valores estáticos const books$ = of([b1, b2, b3]); // creación manual const manual$ = new Observable<number>( observer => { observer.next(1); observer.next(2); observer.complete(); } );
03
Observables

subscribe + cleanup

export class BookListComponent implements OnInit, OnDestroy { private subscriptions = new Subscription(); ngOnInit() { this.subscriptions.add( books$.subscribe({ next: (books) => this.books = books, error: (err) => console.error(err), complete: () => console.log('completado'), }) ); } ngOnDestroy() { this.subscriptions.unsubscribe(); // cancela todas a la vez } }

Siempre hacer unsubscribe — si no, memory leak: el observer queda enganchado aunque el componente se destruya.

03
Observables

Subject & BehaviorSubject

Subject

Observable que también puede emitir. Útil para event buses internos.

private subj = new Subject<Book[]>(); books$ = this.subj.asObservable(); refresh() { this.subj.next(this.books); }

BehaviorSubject

Subject con valor inicial que emite a cada nuevo suscriptor.

private subj = new BehaviorSubject<Book[]>([...booksMock]); books$ = this.subj.asObservable(); total$ = this.books$.pipe( map(b => b.length) ); addBook(b: Book) { this.subj.next( [...this.subj.getValue(), b] ); }

El nuevo modelo de reactividad (v16+)

04
Signals

signal() — valor reactivo

¿Qué es?

  • Un valor que sabe cuándo cambia
  • Cuando cambia, Angular actualiza el DOM automáticamente
  • Sin zone.js hands-on — es la base del futuro Angular zoneless
  • Se lee como función: count()

Definir y mutar

import { signal } from '@angular/core'; count = signal(0); increment() { // update — basado en el valor previo this.count.update(v => v + 1); // o set — reemplaza directo this.count.set(this.count() + 1); }

En el template: {{ count() }} — la signal se lee como función, no como propiedad.

04
Signals

computed() & effect()

computed — valor derivado

books = signal<Book[]>([]); selected = signal(''); totalBooks = computed( () => this.books().length ); filtered = computed(() => this.books().filter(b => b.category === this.selected() ) );

Se recalcula solo cuando cambia alguna signal que usa.

effect — side effects

constructor() { effect(() => { console.log( 'libros:', this.books().length ); }); }

Corre al inicio y cada vez que cambia una signal leída adentro. Útil para logging, sync con localStorage.

Patrón puente: dentro de un subscribe() llamás signal.set(...) y dejás que computed() reaccione. Lo mejor de los dos mundos.
