NgModules (Legacy)

@NgModule — estructura básica

import { NgModule } from '@angular/core'; import { BrowserModule } from '@angular/platform-browser'; // HttpClientModule — forma pre-v15 de habilitar HTTP. ELIMINADO en Angular 18. // En proyectos nuevos usar: provideHttpClient(withFetch()) en app.config.ts import { HttpClientModule } from '@angular/common/http'; import { RouterModule } from '@angular/router'; @NgModule({ declarations: [ // componentes, directivas y pipes se declaran aquí AppComponent, BookListComponent, ], imports: [BrowserModule, HttpClientModule, RouterModule.forRoot(routes)], providers: [], // servicios con scope de módulo bootstrap: [AppComponent], // solo en el módulo raíz }) export class AppModule {}

Diferencia clave: NgModule usa declarations + importar el módulo donde se usa. Standalone usa imports directamente en @Component({ imports: [...] }).

📦
NgModules (Legacy)

Lazy loading con NgModule (pre-v17)

Antes — un .module.ts por feature

// app.routes.ts (legacy) { path: 'books', loadChildren: () => import('./books/books.module') .then(m => m.BooksModule) } // BooksModule era un @NgModule // con BooksRoutingModule interno

Ahora — array de rutas directo

// app.routes.ts (standalone) { path: 'books', loadChildren: () => import('./books/books.routes') .then(m => m.booksRoutes) } // booksRoutes es un array de Route[] // — sin @NgModule alguno

Mismo objetivo: generar un chunk JS separado por feature. Cambia la sintaxis, no el resultado de runtime.

📦
NgModules (Legacy)

Migrar un componente — NgModule → standalone

Antes (NgModule)

// declarado en un módulo // sin imports propios @Component({ selector: 'app-book', templateUrl: './book.component.html' }) export class BookComponent {}

Después (standalone)

// self-contained — standalone es default desde v19 // importado donde se usa @Component({ selector: 'app-book', imports: [NgStyle], templateUrl: './book.component.html' }) export class BookComponent {}

Desde Angular v19: standalone: true es implícito — ng update lo remueve automáticamente. Solo poner standalone: false si querés mantener el componente en un NgModule.

02

Lazy Loading Moderno

Cargar JS solo cuando el usuario lo necesita

02
Lazy Loading

¿Por qué lazy loading?

Sin lazy (eager)

Bundle inicial descarga TODO el JS de la app

→ primera carga lenta, incluso secciones que nunca visitan

Con lazy

Cada feature en un chunk JS separado

→ se descarga solo cuando el usuario navega a esa ruta

Cómo se ve

DevTools → Network → filtrar JS

Al navegar a una ruta lazy, ver el chunk descargarse en vivo

Tres formas en Angular standalone: loadComponent (un componente), loadChildren (un grupo de rutas), y @defer (un bloque del template).

02
Lazy Loading

loadComponent — un componente, un chunk

La forma moderna en Angular standalone. Cada loadComponent genera su propio chunk JS separado.

// app.routes.ts — antes (eager): todo se descargaba al inicio // import { AddBookComponent } from './components/add-book/add-book.component'; // { path: 'add-book', component: AddBookComponent, canActivate: [authGuard] }, // Ahora (lazy): chunk descargado solo al navegar a /add-book { path: 'add-book', loadComponent: () => import('./components/add-book/add-book.component') .then(m => m.AddBookComponent), canActivate: [authGuard], }, { path: 'add-book-tdf', loadComponent: () => import('./components/add-book-tdf/add-book-tdf.component') .then(m => m.AddBookTdfComponent), canActivate: [authGuard], },

Verificación: DevTools → Network → filtrar JS → navegar a /add-book → ver el chunk cargarse.

02
Lazy Loading

loadChildren — un grupo de rutas, un chunk

app.routes.ts

{ path: 'books', loadChildren: () => import('./books/books.routes') .then(m => m.booksRoutes), }

Ideal para una "feature" completa: lista + detalle + todas sus dependencias en el mismo chunk.

books/books.routes.ts

import { BookListComponent } from '../components/book-list/book-list.component'; import { BookDetailComponent } from '../components/book-detail/book-detail.component'; export const booksRoutes: Routes = [ { path: '', component: BookListComponent }, // /books { path: ':id', component: BookDetailComponent }, // /books/1 ];

Sin @NgModule: el array de rutas es suficiente. Standalone reemplaza al feature module legacy.

02
Lazy Loading

Providers por ruta — scoped al feature

Cada array de rutas puede declarar providers: una instancia separada del scope global (distinta de providedIn: 'root').

export const booksRoutes: Routes = [ { path: '', providers: [BookService], // instancia local al feature 'books' component: BookListComponent }, { path: ':id', component: BookDetailComponent } ]; // Resultado: BookService tendrá una instancia separada // — distinta del providedIn: 'root'

Organización sin NgModules:

src/app/
  books/
    books.routes.ts  ← entry del chunk lazy
  components/
    book-list/
    book-detail/

Uso típico: servicios que deben vivir mientras el feature está activo y destruirse al salir.

03

@defer blocks

Lazy loading nativo en el template — Angular 17+

03
@defer

Carga diferida en el template

No solo rutas — secciones del template. Angular genera un chunk JS separado para el contenido del bloque @defer.

// book-detail.component.html @defer (on viewport) { <!-- BookReviewsComponent: chunk descargado al scrollear --> <app-book-reviews [bookId]="book.id" /> } @placeholder { <!-- Visible inmediatamente, antes de que el chunk descargue --> <p>↓ Scroll to load reviews</p> } @loading (minimum 500ms) { <!-- Visible mientras descarga (mínimo 500ms para evitar flash) --> <p>Loading reviews...</p> } @error { <p>Could not load reviews.</p> }

Caso de uso ideal: secciones no críticas para la primera carga — reviews, comentarios, ads, charts, mapas.

03
@defer

Cómo funciona on viewport — paso a paso

1

Render inicial

Solo el @placeholder. Chunk JS NO descargado.

↓ Scroll to load
chunk.js — not loaded
2

Entra al viewport

IntersectionObserver dispara el trigger.

↓ Scroll to load
⚡
observer → trigger
3

Descarga del chunk

dynamic import() — se muestra @loading.

⟳ Loading...
chunk.js — downloading
4

Componente renderizado

Placeholder reemplazado por <app-book-reviews>.

★★★★☆ Reviews
chunk.js — cached ✓

Una sola descarga por sesión: si el usuario scrollea hacia arriba y abajo de vuelta, el chunk queda cacheado en memoria — no se vuelve a pedir a la red.

03
@defer

¿Qué ve el usuario? — con vs sin @loading

Con on viewport el placeholder es fugaz — apenas entra al viewport, el trigger dispara y @loading lo reemplaza casi inmediatamente.

Con @loading

@placeholder ~16 ms
→
@loading ~download
→
componente stable

Caso típico. El placeholder sirve solo como anchor del observer; el usuario percibe el spinner de loading.

Sin @loading

@placeholder ~download
→
componente stable

El placeholder queda visible durante toda la descarga. Útil si el mensaje del placeholder es informativo de por sí (ej: "↓ Scroll to load reviews").

Tuning fino: @loading (after 200ms; minimum 500ms) — no muestres loading si el chunk tarda menos de 200ms (evita parpadeo en redes rápidas), y una vez visible, mantenelo al menos 500ms (evita parpadeo del loading mismo).

03
@defer

Triggers — cuándo dispara la carga

on viewport

Cuando el @placeholder entra al viewport — perfecto para contenido "below the fold".

on interaction

Al hacer click, focus o touch — útil para modales y secciones expandibles.

on hover

Al pasar el mouse — para tooltips ricos o previews.

on idle

Cuando el browser no tiene trabajo pendiente — precargar sin afectar la UX.

when <expr>

Cuando una expresión es verdadera: @defer (when isLoggedIn) { ... } — control completo desde el código.

Combinable: @defer (on viewport; on idle) — dispara con el primero que ocurra.

toSignal()

El bridge entre Observables y Signals

04
toSignal

Observable → Signal en una línea

Convierte un Observable en una Signal — combina la potencia de RxJS con la ergonomía de Signals. Debe llamarse en un injection context.

import { toSignal } from '@angular/core/rxjs-interop'; export class BookListComponent { // vm$ sigue siendo el Observable con toda la lógica (no cambia) vm$ = this.refresh$.pipe( switchMap(() => this.route.queryParams), switchMap(params => forkJoin({ books: ..., categories: ... })), catchError(...), ); // toSignal: se suscribe a vm$ y expone el último valor como Signal // initialValue: null = "aún no cargado" (igual que async pipe antes del primer emit) vm = toSignal(this.vm$, { initialValue: null }); }

Cleanup automático: toSignal cancela la subscripción cuando el componente se destruye — igual que | async, pero sin pipe.

04
toSignal

async pipe vs toSignal()

Lección 5 — async pipe

// requiere AsyncPipe en imports @Component({ imports: [AsyncPipe, ...], template: ` @if (vm$ | async; as vm) { ... } ` })

Lección 6 — toSignal

// vm() es una Signal, no necesita pipe @Component({ imports: [...], // sin AsyncPipe template: ` @if (vm(); as vm) { ... } ` })

Ventajas de toSignal: no requiere importar AsyncPipe, tipo más preciso, más composable con computed() y effect().

04
toSignal

Patrón "store" con Signals — sin librerías

@Injectable({ providedIn: 'root' }) export class BookStore { private _books = signal<Book[]>([]); private _loading = signal(false); private _selectedCategory = signal<string | null>(null); // Readonly para consumidores — no pueden escribir desde afuera readonly books = this._books.asReadonly(); readonly loading = this._loading.asReadonly(); // Computed — derivado, recalcula cuando _books o _selectedCategory cambian readonly filteredBooks = computed(() => { const cat = this._selectedCategory(); return cat ? this._books().filter(b => b.categories.includes(cat)) : this._books(); }); readonly totalBooks = computed(() => this._books().length); selectCategory(cat: string | null) { this._selectedCategory.set(cat); } }

Deploy

Deploy a Firebase Hosting

¿Por qué Firebase?

  • Deploy en un solo comando
  • HTTPS automático + CDN global
  • SPA rewrite a index.html nativo
  • Dominio gratuito *.web.app
  • Plan Spark (free) — sin tarjeta de crédito

Spark plan: 10 GB storage, 360 MB/día de transferencia. Más que suficiente para portfolios.

Build + deploy

bash
$npm install -g firebase-tools
$firebase login
$ng build
# Salida: dist/book-store/browser/
$firebase init
# Hosting + public dir + SPA rewrite: Yes
$firebase deploy
# → https://[proyecto].web.app

SPA rewrite es crítico: sin él, refrescar /books/1 tira 404.
